Start here

This tool answers one question: how much engineering time will this Concept-phase work package take, and what number is safe to put in a Statement of Work?

Instead of scoring a work package against fixed 1/2/3 dimensions, you give each one an honest three-point time estimate — optimistic, most likely, pessimistic — plus a complexity multiplier. The tool combines those into an Expected hours figure (for internal planning) and a P80 commitment figure (safe to quote externally). This is the same estimating method — PERT plus a complexity multiplier plus contingency plus a percentile commitment — used in the reference estimator this scorer was adapted from.

Your first five minutes

1. Delete any pre-filled work package that doesn't apply to this project, rename ones that are close, add anything missing.
2. Expand one row and fill in three hour estimates. Don't agonize — you'll refine them.
3. Set the complexity multiplier — how unfamiliar is this specific package, not the project as a whole.
4. Check the sidebar for the two headline figures: Expected effort and P80 commitment.

How the scoring works

Each step below catches a different kind of estimating error. They stack in order.

1. Three numbers, not one

Asking for one number gets you the version of the task where everything goes right, because that's the version people picture. Three numbers force a wider view:

EstimateMeans
Optimistic (O)Everything goes right — no rework, no waiting. Still a genuinely possible outcome, not fantasy.
Most Likely (M)Your honest normal expectation, with the usual amount of friction.
Pessimistic (P)A realistic bad run — rework, a wrong assumption, waiting on someone. Not a catastrophe.

The gap between O and P is information, not padding. Squeezing it to look confident throws away the only measurement of uncertainty the tool has.

2. Combine them (PERT)

A plain average lets a long pessimistic tail drag the number too high, because task durations are skewed — there's a floor on how fast work can go, but no ceiling on how slow. PERT weights Most Likely four times as heavily as the two extremes:

Expected hours = (O + 4 × M + P) ÷ 6

This is established method (Program Evaluation and Review Technique, US Navy, 1950s), not a heuristic invented for this tool.

3. Measure the uncertainty (σ)

σ = (P − O) ÷ 6

σ (sigma) is the typical amount reality differs from the middle estimate. Small σ means outcomes cluster tightly; large σ means they scatter widely. It's what turns "137.5 hours" into a range instead of a false-precision point figure.

4. Correct for unfamiliar work (complexity multiplier)

Even a pessimistic guess is anchored to problems you've already seen — you can't imagine a failure mode you've never encountered. The complexity multiplier corrects the center of the estimate for that blind spot. See Complexity multiplier below.

5. Add contingency

Contingency buffers project-level friction that belongs to no single work package — approval delays, vendor lead times, integration surprises. It's applied on top of the multiplier, centrally managed rather than set per package. See Contingency & risk correlation below.

6. Roll up to a phase total

Hours just add up. Uncertainty doesn't — see Contingency & risk correlation for why the phase range uses a correlation factor instead of a linear sum.

7. Pick a commitment number

The Expected value is the middle of the range — you'd overrun it about half the time. For a figure you'll put in a customer-facing document, the tool also gives P80. See What "Score" means.

What "Score" means

This tool doesn't produce a single "score" the way the old 1/2/3 dimension grid did. Every work package — and the phase total in the sidebar — shows two numbers, and they answer two different questions:

NumberFormulaUse it for
Expected (central)the PERT-derived middle, × multiplier, × (1 + contingency)Internal planning, resourcing. You'd overrun it roughly half the time — that's fine for planning, where overs and unders average out.
P80Expected + 0.84 × σBinding SOW commitments, customer-facing quotes. The figure you'd expect to come in under about 80% of the time — 1 overrun in 5 instead of 1 in 2.

This is exactly what the reference estimator (the jsx your boss sent over) calls "Expected effort" and "P80 commitment" side by side on its Summary tab — nothing was renamed or reinterpreted here. If someone asks "what's the score for this package," the honest answer is "which one — Expected or P80?"

The per-package Score column in the grid shows Expected as the large number and P80 as the smaller line underneath, colored by that package's complexity tier. The sidebar shows the phase-wide totals for both.

Complexity multiplier

The multiplier corrects for the planning fallacy (Kahneman & Tversky, 1979) — the documented tendency to underestimate novel work even when you know about the tendency, because you can't picture a problem you've never met.

MultiplierWhen to use itExamples
1.0You've built this exact type of thing before.Off-the-shelf robot + standard gripper. A layout done 5+ times.
1.2 – 1.4Familiar territory, with a new twist.Same robot family, different payload/reach.
1.5 – 2.0Meaningful customization.Custom end-effector with new actuation. Unfamiliar PLC/vendor ecosystem.
2.5 – 3.0+Genuinely novel — no internal precedent.Custom kinematic mechanism. First-of-kind sensor fusion.

Apply it per work package, not as one blanket project number — a layout using an off-the-shelf robot might be 1.0 while a custom end-effector on the same project is 2.0. This tool flags any package at 2.5x or higher on the Concept decision box.

Avoid double-counting: if your Pessimistic hours already assume "this could be a slog because it's new to us," don't also apply a large multiplier for the same reason.

Contingency % & risk correlation

These two numbers are centrally managed in the shared Config tab (concept.contingency_pct and concept.correlation) rather than sliders on this page — so every RSE and SDE scores against the same assumptions instead of picking their own.

Contingency %

Buffers project-level friction that isn't part of any single work package's own variance — approval delays, vendor lead times, integration surprises between subsystems. AACE International's cost estimate classification system ties it to design maturity: roughly 20–30% at Concept-level, dropping to 10–15% once detailed design is underway.

Risk correlation

Individual work packages' uncertainties don't simply add up. If every package's risk were independent, some would run over while others ran under and partly cancel — the combined uncertainty would be √(Σσ²), narrower than the linear sum. If everything is driven by one shared cause (a bad early requirements assumption), they'd stack linearly. Reality sits between, so the phase total uses a correlation factor (currently defaulting to 35%) instead of either extreme.

Summing each package's low/high linearly would silently assume 100% correlation and produce a range that looks like "±1σ" but isn't. The correlation factor replaces that silent assumption with an explicit, adjustable one.

What this tool can't do

None of these are bugs — they're boundaries worth knowing before trusting a number further than it deserves.

It cannot make a bad estimate good. Every number here traces back to someone's three guesses. PERT, the multiplier, and contingency reduce specific, known biases in those guesses — none of them add information that wasn't there.

It doesn't know what you forgot. The most common cause of a badly wrong estimate is a task nobody listed, not a task that ran long. Walk the work package list with someone else and ask what's missing.

The multiplier scale and contingency defaults are heuristics, not standards. They're reasonable starting points, not published industry standards for robotics engineering.

It only covers Concept-phase engineering hours. No cost or calendar-duration modeling, no build/commissioning effort.

The reference estimator this was adapted from also included features intentionally left out here for now: multiple independent estimators per package with a divergence check, an Actuals & Calibration tab comparing estimates to real outcomes over time, concurrency/phase-overlap modeling for calendar duration, and Shared vs. Task-Specific decomposition for multi-capability solutions. All of those are portable if this tool proves out and it's worth building them.

Glossary

Work package
A discrete chunk of Concept-phase engineering work, small enough to picture doing and distinct enough not to overlap another one. One row in the grid.
Three-point estimate
Giving three time guesses instead of one, so the estimator has to consider more than the best case.
PERT
Program Evaluation and Review Technique — combines three estimates into one weighted number: (O + 4M + P) ÷ 6.
Standard deviation (σ)
The typical amount reality differs from the middle estimate. Here, σ = (P − O) ÷ 6.
Complexity multiplier
A correction that scales the estimate's center up based on how novel the work is. 1.0x = routine, 3.0x = first-of-kind.
Contingency
A percentage buffer for project-level friction belonging to no single work package. Centrally managed for this tool.
Expected value (central estimate)
The middle of the range. You'd overrun it roughly half the time. Use for internal planning.
P80 / P90
The figure you'd expect to come in under 80% (or 90%) of the time. P80 is this tool's default commitment figure.
Risk correlation
How much work packages tend to go wrong together. 0% = independent risks that partly cancel; 100% = one shared cause affects everything.
Planning fallacy
The documented tendency to underestimate how long tasks take, worse for unfamiliar work because you can't imagine a problem you've never met.
